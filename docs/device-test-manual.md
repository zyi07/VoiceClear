# VoiceClear 真机测试手册

> 适用版本：**0.11.1**（`versionCode` 12）  
> 编制日期：2026-11-17  
> 适用设备：Android 真机（首版目标：华为 / 荣耀，Android 12 及以上）

---

## 0. 这份手册的定位

### 0.1 为什么需要人工实测

自动化 UI 测试（Espresso）在当前环境跑不起来：构建机没有 `/dev/kvm`，
无法启动模拟器；而当前构建环境也没有连接可用真机。更重要的是——
**本项目的核心不确定性无法用自动化断言表达**：

- 目标人群（听障相关发音不清的普通话成人）的识别可用性，
  要靠人判断"这句话识别得对不对、能不能用"，不是断言能覆盖的；
- 音频路由、来电中断、蓝牙断连这些场景需要真实硬件；
- 温升与耗电需要连续真实使用。

所以这份手册把人能判断的部分写成**可执行的步骤 + 可判定的标准**，
让每一次实测都能产出**可比较的数据**，而不是"感觉好点了"。

### 0.2 覆盖范围

| 分组 | 内容 | 谁来测 |
|---|---|---|
| A | 启动、模型加载、内存 | 任何人 |
| B | 基本表达流程 | 任何人 |
| C | 音频质量与麦克风音源对比 | 任何人 |
| D | 异常与中断场景 | 任何人 |
| E | 长时使用与资源占用 | 任何人 |
| F | **目标人群识别效果** | **必须目标用户，且有知情同意** |

A-E 组任何人都能做，用于验证**工程稳定性**。
F 组只能由目标用户参与，用于验证**产品可用性**——这两件事不能互相代替。

### 0.3 不在本轮范围

见第 7 节。简要说：不测多语言、不测平板布局、不测 Android 12 以下、
不测证书锁定与文件加密（本期未实现，见审计报告附录 A.3）。

## 1. 测试前准备

### 1.1 设备与环境

| 项 | 要求 |
|---|---|
| 设备 | 你的华为 / 荣耀真机（当前实测机型：HUAWEI PLA-AL10） |
| 系统 | Android 12 (API 31) 及以上 |
| 存储 | 至少 1 GB 可用（模型约 239 MB，另加临时空间） |
| 网络 | 仅首次下载模型需要网络；**识别全程离线** |
| 环境 | 每组测试尽量固定在同一房间，便于比较 |

**建议准备两样东西**：

1. **秒表**（手机自带即可）——测等待时间用，不要靠感觉估计；
2. **一句话**——C 组音源对比要用同一句话反复说，先想好写下来。

### 1.2 安装

1. 把 `VoiceClear-debug-0.11.1-manual-test.apk` 传到手机（微信文件传输 / 数据线 / adb 均可）。
2. 点击安装。若提示"未知来源"，允许本次安装即可。
3. 安装完成后**先不要打开**，做完 1.3 再打开。

> 若手机上已有旧版本，直接覆盖安装。系统会保留原有设置与已下载的模型。

### 1.3 首次启动与模型下载

1. 打开应用，观察主界面底部模型状态行。
2. 若显示模型未就绪，点「模型下载」按钮，等待完成（约 239 MB，视网速 1-10 分钟）。
3. 下载完成后，状态行应变为「离线识别模型已就绪（xxx MB）」。

**下载失败时**：应用会自动换源重试（ModelScope → GitHub Release）。
若两个源都失败，请导出诊断包（见 1.4）并发回，日志里会有每个源的失败原因。

### 1.4 日志导出与回传（每次测试结束都要做）

1. 主界面点「**导出全部诊断信息**」。
2. 系统弹出文件保存位置，选容易找的地方（如"下载"目录），确认保存。
3. 文件名形如 `voiceclear-diagnostics-<时间戳>.zip`。

**包里有什么**：

| 文件 | 内容 |
|---|---|
| `app-log.txt` | 结构化日志：各阶段耗时、音频 RMS/峰值、错误码 |
| `snapshot.txt` | 设备型号、系统版本、内存、权限、音频路由 |
| `metrics.json` | 会话级指标 |
| `benchmark.json` | 最近一次识别的基准 |
| `benchmark-summary.json` | **最近 50 次的中位数与 P95**（本轮重点） |
| `crash.txt` | 崩溃堆栈（如有） |
| `SHA256SUMS.txt` | 包内各文件的哈希清单 |
| `README.txt` | 上述说明 |

**包里没有**：原始音频、完整表达文本、任何个人身份信息。
（日志只记文本长度，不记文本内容。）

**回传前建议校验一下**（可选，但能确认文件传输没损坏）：

```bash
unzip voiceclear-diagnostics-<时间戳>.zip -d diag
cd diag && sha256sum -c SHA256SUMS.txt
```

全部显示 `OK` 说明包完整。若有 `FAILED`，说明传输过程出错，请重新导出。

### 1.5 记录方式

每个用例测完，**当场**把结果填进第 4 节的表格。
不要等全部测完再回忆——尤其是耗时和"当时说了什么"。

## 2. 测试用例

每个用例的写法：**目的 → 步骤 → 预期 → 要记录什么**。
标 `[可选]` 的用例耗时较长或需要特殊条件，时间紧可跳过，但要在结论里注明跳过。

### A 组：启动、模型与内存

#### TC-A1 冷启动与模型加载

**目的**：确认冷启动在可接受时间内可用，采集基线数据。

**步骤**：

1. 从最近任务里把 VoiceClear 划掉（确保进程已退出）；
2. 回到桌面，点图标启动，**同时开始计秒**；
3. 盯着状态行，直到显示「准备就绪」且模型行显示就绪。

**预期**：≤ 3 秒内进入可录音状态。

**记录**：启动到可用的秒数；模型行显示的 MB 数。

> 参考值（同一台 PLA-AL10 之前实测）：冷启动 138 ms，模型加载 1158 ms。
> 若明显超过 5 秒，导出诊断包，日志里的 `I/Main: 识别引擎就绪 ... 加载耗时=` 会给出准确数字。

#### TC-A2 温启动（切回前台）

**目的**：确认从后台切回不需要重新加载模型。

**步骤**：

1. 应用在前台且已就绪；
2. 按 Home 键回桌面，停留 10 秒；
3. 从最近任务切回应用。

**预期**：立即可用，无需等待模型重新加载，状态仍为「准备就绪」。

**记录**：切回后是否立即可用（是 / 否 + 等待秒数）。

#### TC-A3 模型内存不足时的提示

**目的**：验证内存不足时给出可读提示，而不是闪退。

**步骤**：

1. 从最近任务划掉 VoiceClear；
2. 连续打开 5-8 个占用内存的应用（相机、地图、短视频类各开一个更好）；
3. 保持它们都在后台，**不清理**；
4. 打开 VoiceClear。

**预期**（两种都算通过，但含义不同）：

- **情况一**：正常加载完成 → 说明这台设备内存足够，记录"未触发"。
- **情况二**：状态行显示「可用内存不足，无法加载识别模型。请关闭其他后台应用后重新打开本应用。」，
  且**应用不崩溃**、不显示模型下载按钮 → 说明保护逻辑生效。

**记录**：触发的是情况一还是情况二；若情况二，诊断包里 `snapshot.txt` 的 `vmMaxHeapMb` 值。

**失败判定**：应用闪退、白屏、无提示卡住 → 记为缺陷。

#### TC-A4 权限拒绝后的恢复

**目的**：确认麦克风权限被拒后，重新授权能正常使用。

**步骤**：

1. 系统设置 → 应用 → VoiceClear → 权限 → 麦克风，改为**不允许**；
2. 回到应用，点「开始录音」；
3. 应用应弹出权限请求或提示「未获得麦克风权限」；
4. 允许权限，再点「开始录音」说一句话。

**预期**：第 2 步不崩溃并给出提示；第 4 步正常录音并按 B1 流程完成识别。

**记录**：第 2 步看到的提示文字；第 4 步是否成功。

#### TC-A5 强制停止后重启

**目的**：确认进程被系统杀掉后能干净恢复。

**步骤**：

1. 系统设置 → 应用 → VoiceClear → **强行停止**；
2. 重新打开应用；
3. 按 B1 说一句话完成一次表达。

**预期**：正常启动、模型就绪（无需重新下载）、可完成一次完整表达。

**记录**：是否需要重新下载模型（应为否）；是否完成一次表达。

### B 组：基本表达流程

#### TC-B1 完整流程（核心用例）

**目的**：验证主干路径端到端可用。**这是最重要的一条。**

**步骤**：

1. 手机竖持，离嘴约 15-20 cm，屏幕朝上；
2. 点「开始录音」（按钮变为「停止」，状态显示「正在录音…」）；
3. 用平常音量、稍慢语速说一句 2-4 秒的话，例如「我想喝水」；
4. 点「停止」；
5. 等待状态变为「请确认识别结果」，看识别文本框的内容；
6. 若文字正确，点「确认并播放」；
7. 听合成语音是否把这句话说出来。

**预期**：

- 第 5 步在 **2 秒内**出现可确认文本；
- 文本与所说内容语义一致（错字但意思对，算通过 B1，错字记入 F 组质量统计）；
- 第 7 步能听到合成语音，内容与确认文本一致；
- 状态最终显示「完成」。

**记录**：

| 项 | 值 |
|---|---|
| 说的原话 | |
| 识别出的文本 | |
| 第 5 步等待秒数 | |
| 合成语音是否正常 | 正常 / 异常（异常描述） |

> **连续做 5 次**，分别记录。这 5 次的结果会进 `benchmark-summary.json`，是后续版本对比的基线。

#### TC-B2 纠正识别结果后确认

**目的**：验证人工纠正可绕过识别错误——这是本产品**关键的安全网**。

**步骤**：

1. 说一句容易识别错的话（如包含人名或数字："我下午三点要去银行"）；
2. 停止后，在识别文本框里**手动修改**成正确的文字；
3. 点「确认并播放」。

**预期**：修改后的文字被完整合成并播放；修改过程顺畅（光标定位、输入无障碍）。

**记录**：修改是否顺畅；合成内容是否等于修改后的文字。

#### TC-B3 播放原始语音

**目的**：验证"回放自己刚才的声音"这条兜底路径。

**步骤**：

1. 完成一次录音（不必确认）；
2. 点「播放原始语音」。

**预期**：能听到刚才录的声音，音质与正常录音相当。

**记录**：是否听到；音量是否正常（过小 / 正常 / 过大）。

#### TC-B4 取消流程

**步骤**：

1. 说一句话，停止；
2. 在确认页点「取消」。

**预期**：状态变为「处理失败，请重试或播放原始语音」之外的中性状态，无崩溃；
**随后**能立刻开始新的录音。

**记录**：取消后能否立刻再次录音（是 / 否）。

#### TC-B5 30 秒上限

**目的**：验证超长录音的截断与提示。

**步骤**：

1. 点「开始录音」；
2. 连续说话（或持续发声）超过 35 秒；
3. 观察状态变化，然后点「停止」。

**预期**：

- 30 秒时采集自动停止（不必手动点停止）；
- 识别完成后提示「已达最长录音时间（30 秒），超出部分未被录入。」；
- 不崩溃，且能开始下一次录音。

**记录**：是否出现该提示；超出部分是否确实未出现（说一个词在 32 秒处，看识别结果里有没有）。

#### TC-B6 误触（极短点击）

**目的**：验证点击过快时不产生无意义的识别结果。

**步骤**：

1. 点「开始录音」，**立即**（0.1-0.2 秒内）再点「停止」。

**预期**：

- 不崩溃；
- 若录音不足 200 ms，给出「未采集到有效语音」或「没有听到声音」这类提示；
- **不应**出现一段莫名其妙的文字。

**记录**：看到的提示文字；是否出现莫名其妙的识别结果。

### C 组：音频质量与麦克风音源

> **这组是当前最关键的一组。** 上一轮真机日志里 7 次录音有 5 次几乎完全无声音
> （RMS ≤ 0.0001），模型在这些输入上会产生幻觉输出。
> 这组要回答的问题是：**哪种音源设置在你的设备上更好**。

**先定一句话**：选一句 3-4 秒、你自己说得多的话，例如「今天下午我想去一趟医院」。
写在下面，后面两轮都用它：**__________________________**

#### TC-C1 音源对比 A：原始声音

**步骤**：

1. 点「麦克风设置」→ 选「**原始声音（推荐）**」；
2. 用上面那句话，按 B1 流程说 **5 次**；
3. 导出诊断包，命名时可记为 `A-原始`；
4. 记录每次的 RMS 与识别结果（RMS 在日志里，见下方说明）。

#### TC-C2 音源对比 B：语音识别优化

**步骤**：

1. 点「麦克风设置」→ 选「**语音识别优化**」；
2. 用**同一句话**再说 **5 次**；
3. 导出诊断包，记为 `B-识别优化`；
4. 同样记录 RMS 与识别结果。

**怎么拿到 RMS**：导出包里的 `app-log.txt` 中，每次识别有一行形如：

```
I/Quality: 音频质量: NORMAL, RMS=0.0446, 峰值=0.3828, 有效占比=0.62
```

> 判定参考：`RMS ≥ 0.01` 为正常说话；`0.001-0.01` 偏弱；`< 0.001` 视为没有声音。

**预期**：两次都能正常识别；两组中至少一组识别正确率明显更高。

**记录**（填 5 行）：

| 次数 | 音源 | RMS | 判定档位 | 识别文本 | 与所说是否一致 |
|---|---|---|---|---|---|
| 1 | A / B | | 正常 / 偏弱 / 无声 | | 一致 / 部分 / 错误 |

**结论要写成**：在你这台设备上，A 与 B 哪个更好，依据是「10 次里各识别对几次」。

#### TC-C3 距离梯度

**目的**：找出实际可用的说话距离。

**步骤**：分别用 **5 cm / 15 cm / 30 cm** 说同一句话各 2 次。

**预期**：15 cm 表现最好；5 cm 可能因近讲效应变差；30 cm 可能因能量不足变差。

**记录**：

| 距离 | RMS | 识别是否正确 | 备注 |
|---|---|---|---|
| 5 cm | | | |
| 15 cm | | | |
| 30 cm | | | |

#### TC-C4 噪声梯度

**目的**：确认在真实环境噪声下的可用性边界。

**步骤**：在三类环境各说同一句话 2 次：

1. **安静**（房间内，无电视无风扇）；
2. **日常**（有电视或交谈声）；
3. **嘈杂**（厨房抽油烟机 / 街边 / 公交）。

**记录**：

| 环境 | RMS | 识别是否正确 | 是否出现「没有听到声音」 |
|---|---|---|---|
| 安静 | | | 是 / 否 |
| 日常 | | | 是 / 否 |
| 嘈杂 | | | 是 / 否 |

> 若嘈杂环境出现「没有听到声音」，说明能量判定阈值在实际噪声下偏严，
> 需要一并反馈——这是有价值的发现，不是失败。

### D 组：异常与中断

#### TC-D1 来电 / 闹钟中断

**步骤**：

1. 开始录音；
2. 期间让另一台设备拨入电话（或设一个 30 秒后的闹钟）；
3. 处理完电话/闹钟后回到应用。

**预期**：应用不崩溃；正在合成的语音被正确暂停；回到应用后能立刻开始新的录音。

**记录**：是否崩溃；是否需要重启应用才能继续；播放是否被正确打断。

#### TC-D2 蓝牙耳机切换

**步骤**：

1. 未连接蓝牙时录一次；
2. 连接蓝牙耳机后录一次；
3. 播放合成语音，听声音从哪出。

**预期**：不崩溃；录音可用；播放走当前音频路由（蓝牙或手机扬声器其一，需记录实际是什么）。

**记录**：录音是否可用；播放实际走哪个设备；听感是否异常。

#### TC-D3 有线耳机插拔

**步骤**：录音过程中插入 / 拔出有线耳机各一次。

**预期**：不崩溃。

**记录**：插入/拔出后录音是否仍继续；识别结果是否受影响。

#### TC-D4 快速双击（并发保护）

**目的**：验证上一轮修的并发缺陷不再重现。

**步骤**：

1. 说一句话，**快速连点两次「停止」**；

**预期**：

- 只发生一次识别；
- **不出现**「录音失败」这类错误提示；
- 状态正常进入「请确认识别结果」。

**记录**：是否出现多余的错误提示（这是本用例的核心）；设置结果是否正常。

> 若出现错误提示，请把当时的诊断包发回——日志里会有一条
> `W/Main: 忽略重复的停止请求`，这是正常的；若同时出现 `E/...采集失败`，则是缺陷。

#### TC-D5 确认页误点「开始录音」

**步骤**：

1. 说一句话并停止，停在确认页；
2. 直接点左下角的「开始录音」。

**预期**：提示「上一次表达还没完成。请先点「确认」或「取消」，再开始新的录音。」；
**不应**提示「录音失败」。

**记录**：看到的提示文字。

#### TC-D6 录音中切后台 / 锁屏

**步骤**：

1. 开始录音；
2. 立刻按 Home 键（或按电源键锁屏）；
3. 20 秒后切回应用。

**预期**：不崩溃；应用回到可用状态（可能需重新开始录音，这是可接受的）。

**记录**：是否崩溃；切回后能否立刻录音。

#### TC-D7 旋转屏幕

**步骤**：

1. 完成一次录音，停在确认页；
2. 旋转屏幕；
3. 观察识别文本是否还在，然后点「确认并播放」。

**预期**：识别文本不丢失（由 ViewModel 跨配置变更存活保证）；能正常确认播放。

**记录**：文本是否保留；确认播放是否正常。

#### TC-D8 录音中切换音源（应被拒绝）

**步骤**：

1. 开始录音；
2. 录音中点「麦克风设置」，选另一个音源。

**预期**：提示「正在录音，无法切换麦克风。请先停止录音再切换。」；
**不应**静默丢弃正在进行的录音。

**记录**：提示文字；正在进行的录音是否还在（停止后能否识别）。

### E 组：长时使用与资源

#### TC-E1 连续 20 次完整流程

**目的**：验证长时间反复使用不劣化、不崩溃。

**步骤**：

1. 按 B1 流程连续做 **20 次**（不用每次都说不同的话，说同一句也可以）；
2. 每次记录第 5 步的等待秒数；
3. 做完导出诊断包。

**预期**：

- 20 次全部完成，**0 次崩溃**；
- 等待时间**没有明显变长**（前 5 次平均与后 5 次平均相差不超过 50%）。

**记录**：20 次的等待秒数；崩溃次数；是否有明显卡顿。

#### TC-E2 连续 30 分钟使用（温升与耗电）[可选]

**步骤**：

1. 记录开始时的电量百分比；
2. 每 2 分钟做一次 B1 流程，持续 30 分钟；
3. 结束时记录电量与手机背面温度感受（不烫 / 温热 / 烫手）。

**预期**：电量下降 ≤ 10%；温度不超过「温热」。

**记录**：

| 项 | 值 |
|---|---|
| 起始电量 | |
| 结束电量 | |
| 温感 | 不烫 / 温热 / 烫手 |
| 期间是否崩溃 | |

#### TC-E3 诊断包完整性与聚合数据

**目的**：确认诊断包可用，且 `benchmark-summary.json` 有数据。

**步骤**：

1. 导出诊断包；
2. 解压，执行 `sha256sum -c SHA256SUMS.txt`；
3. 打开 `benchmark-summary.json`。

**预期**：

- 校验全部 `OK`；
- `benchmark-summary.json` 里 `sampleCount` 大于 0，且含
  `recognition` 的 `medianMs` 与 `p95Ms`。

**记录**：校验是否通过；`sampleCount` 数值；`medianMs` / `p95Ms` 各是多少。

### F 组：目标人群识别效果（需目标用户）

> **前提**：这一组**必须**由目标用户（听障相关发音不清的普通话成人）参与，
> 并按 `docs/consent-and-notice-draft.md` 取得知情同意。
> 任何人代测都**不能**得出"目标人群可用"的结论——这是本项目的核心诚实边界。

#### TC-F1 自然表达测试（10 句常用语）

**步骤**：

1. 准备 10 句目标用户在日常生活中真实会说的话
  （例如「我要喝水」「帮我叫医生」「今天不舒服」「我想上厕所」）；
2. 让用户**用自己日常的方式**说，不要刻意放慢或提高音量；
3. 每句做一次完整流程，记录识别结果；
4. 由用户（或熟悉的家属）判断"这句话识别得对不对"。

**判定口径**（三档，必须只按用户判断，不按开发者猜测）：

| 档 | 定义 |
|---|---|
| **可用** | 意思正确，直接用或改一两个字就能用 |
| **部分可用** | 能看出想说什么，但需要明显修改 |
| **不可用** | 看不出原意，或意思被改变 |

**记录**：

| 序号 | 原意 | 识别结果 | 判定 | 备注 |
|---|---|---|---|---|
| 1 | | | 可用 / 部分 / 不可用 | |

#### TC-F2 关键信息保真测试

**目的**：验证**否定词与数字**不被悄悄改掉——这是最危险的一类错误。

**步骤**：说 5 句包含否定或数字的话，例如：

1. 「我**不**想吃药」
2. 「**不**要叫救护车」
3. 「我下午**三**点要去医院」
4. 「我要**两**片」
5. 「今天**不**疼了」

**预期**：否定词（不 / 别 / 没有）与数字必须保留。

**记录**：

| 序号 | 关键信息 | 识别结果是否保留 | 错误类型 |
|---|---|---|---|
| 1 | 否定「不」 | 保留 / 丢失 / 改变 | |

> 若出现「否定词丢失」或「数字改变」，**无论其他用例多好，都要单独报为高危缺陷**——
> 这类错误会让表达的意思反转，风险远高于普通的错字。

#### TC-F3 可用性主观评分

**目的**：拿到"愿不愿意用"的直接信号，这比准确率数字更接近产品成败。

**步骤**：让用户在 1-5 分上打分（可口头回答，测试者记录）：

| 问题 | 1 分 | 5 分 | 得分 |
|---|---|---|---|
| 识别结果能表达我的意思吗 | 完全不能 | 基本都能 | |
| 等待时间可以接受吗 | 太慢，不想用 | 很快，没感觉 | |
| 愿意在日常中用它吗 | 不愿意 | 愿意 | |

**记录**：三项得分 + 用户原话（至少记一句，原话比分数有信息量）。

## 3. 判定标准

### 3.1 客观阈值

| 指标 | 通过标准 | 依据 |
|---|---|---|
| 崩溃次数 | **0** | 任何崩溃都是缺陷 |
| 冷启动到可用 | ≤ 3 秒 | 参考实测 138 ms + 模型 1158 ms |
| 停止到出现可确认文本 | ≤ 2 秒 | 参考实测识别 80-170 ms |
| 实时率（RTF） | < 1.0 | `benchmark-summary.json` 的 `medianRtf` |
| 正常说话 RMS | ≥ 0.01 | `AudioQuality` 阈值 |
| 静音判定 | RMS < 0.001 时提示"没有听到声音" | 同上 |
| 诊断包校验 | `sha256sum -c` 全部 OK | 传输完整性 |
| 20 次连续流程 | 全部完成、0 崩溃、等待时间不劣化 > 50% | E1 |

### 3.2 通过 / 不通过的总体口径

| 组 | 通过条件 |
|---|---|
| A | 5 条用例均达预期，**0 崩溃** |
| B | 6 条达预期；B1 五次中至少 4 次识别语义正确 |
| C | 两组音源都能识别；能给出"A 与 B 哪个更好"的明确结论 |
| D | 8 条均不崩溃；D4、D5、D8 的提示文案与预期一致 |
| E | E1、E3 通过（E2 可选） |
| F | **不作通过/不通过判定**，只产出数据 |

> F 组不设通过线是刻意的：目标人群的识别可用性目前**没有任何基线数据**，
> 本轮的任务是**建立第一个基线**，而不是去够一条凭空的分数线。

## 8. 伦理与合规提醒

这一节不是走流程，是本项目的硬约束：

1. **主界面录音不落盘**：主流程只在内存中处理音频，用于即时识别，
   不写入磁盘、不上传。（诊断日志只记长度与耗时，不记音频与文本。）
2. **采集模式会落盘**：点「采集模式」进去的录音会写入应用私有目录，用于构建数据集；
   录音按 30 天自动过期清理，但**转写与同意书不会被自动删除**。
   请勿在未经同意的目标用户身上使用采集模式。
3. **目标用户参与需知情同意**：F 组开始前，请按 `docs/consent-and-notice-draft.md`
   向参与者说明用途、保存期限、撤回方式，并取得同意。
4. **诊断包可安全外发**：包内不含音频、不含完整文本、不含身份信息，
   可以放心发回分析。若你手动往包里加过任何材料，请先确认不含个人信息。
5. **撤回权**：参与者随时可以要求删除自己的数据；
   应用内「清空采集数据」会显式删除，符合"撤回后不再留存"的要求。

## 9. 建议的测试顺序

时间紧的话，按这个顺序做，价值密度最高：

1. **TC-B1×5**（主干可用性 + 性能基线）
2. **TC-C1 / TC-C2**（音源对比——这一轮的核心目的）
3. **TC-E3**（确认诊断包与聚合数据可用）
4. **TC-D4 / D5 / D8**（上一轮修过的缺陷，验证不复发）
5. **TC-A3**（内存保护，验证不再闪退）
6. 其余按组补齐

F 组单独安排——不要和 A-E 混在同一次里做，
因为它需要目标用户在场并已完成知情同意。
